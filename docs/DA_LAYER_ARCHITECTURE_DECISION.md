## 1. 概述

本文档记录Spora DA（数据可用性）层的架构决策，包括三个核心承诺字段的设计 rationale、职责分离原则以及实现阶段规划。

## 2. 核心架构决策

### 2.1 三个承诺字段的定义

| 字段 | 承诺内容 | 计算方式 | 核心用途 |
|------|----------|----------|----------|
| **`cell_root`** | Live Cell状态的Merkle根 | `CellStateTree.root()` (MuHash) | 状态证明、轻客户端验证Cell存在性 |
| **`cell_commitment`** | 版本化的Cell承诺包装 | `H("spora/cell_commitment/v0" \|\| cell_root)` | 共识校验、未来扩展 |
| **`segment_root`** | Cell大数据的[NMT](#33-nmt-namespaced-merkle-tree)根 | Segment封口时计算NMT | 数据可用性验证、抗数据扣留 |

## 3. 决策分析

### 3.1 三者是否重合？

**结论：三者职责分离，不会重合，但有依赖关系**

| 对比维度 | cell_root | segment_root | 是否重叠 |
|----------|-----------|--------------|----------|
| **承诺的数据** | Cell元数据（小） | Cell大数据（大） | ❌ 不重叠 |
| **数据位置** | RocksDB（索引层） | Segment文件（DA层） | ❌ 分离存储 |
| **验证方式** | Merkle/MuHash证明 | NMT抽样验证 | ❌ 不同机制 |
| **轻客户端用途** | 验证"Cell存在" | 验证"数据可用" | ❌ 互补 |

### 3.2 cell_commitment是否多余？

**结论：不多余，版本化抽象必要**

| 场景 | 没有cell_commitment | 有cell_commitment |
|------|---------------------|-------------------|
| 协议升级 | 需要硬分叉修改cell_root语义 | 只需升级commitment版本 |
| 多根承诺 | 区块头字段膨胀 | 一个字段承诺多个根 |
| 验证复杂度 | 需要知道版本才能验证 | 版本自描述 |

**未来扩展路径**：
```rust
// V0: 当前
// cell_commitment = H("spora/cell_commitment/v0" || cell_root)

// V1: 未来添加DA承诺
// cell_commitment = H("spora/cell_commitment/v1" || cell_root || segment_root)

// V2: 未来添加更多索引
// cell_commitment = H("spora/cell_commitment/v2" || cell_root || segment_root || script_index_root)
```

### 3.3 segment_root是否必要？

**结论：长期必要，短期可选**

| 场景 | 是否必须 | 说明 |
|------|----------|------|
| **共识安全** | ❌ 非必须 | `cell_root`已足够保证状态一致性 |
| **轻客户端数据可用性验证** | ✅ 必须 | 没有`segment_root`，轻客户端无法验证大数据Cell是否被真正发布 |
| **全节点运行** | ❌ 非必须 | 全节点可以直接存储完整数据 |
| **抗数据扣留攻击** | ✅ 必须 | DA层的核心目的 |

**核心区别**：
- `cell_root`告诉你"Cell存在且状态正确"
- `segment_root`保证"Cell的大数据可以被网络获取"

### 3.3 NMT (Namespaced Merkle Tree)

**NMT**是专门为数据可用性（DA）设计的Merkle树变体，由Celestia引入，用于解决轻客户端的数据可用性验证问题。

#### 3.3.1 为什么需要NMT？

| 问题 | 传统Merkle树 | NMT解决方案 |
|------|-------------|-------------|
| **数据类型混杂** | 所有数据混合在一个树中 | 引入**命名空间（Namespace）**，不同类型数据隔离 |
| **抽样效率低** | 随机抽样可能集中在同一类型 | 可按命名空间定向抽样 |
| **证明大小** | 与数据量线性相关 | 通过命名空间压缩证明路径 |

#### 3.3.2 NMT核心特性

```
┌─────────────────────────────────────────────────────────────────┐
│                     NMT 结构示意                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌───────────────────────────────────────────────────────┐    │
│   │                    NMT Root                            │    │
│   │              (包含所有命名空间的承诺)                    │    │
│   └───────────────────────┬───────────────────────────────┘    │
│                           │                                     │
│           ┌───────────────┼───────────────┐                    │
│           ▼               ▼               ▼                    │
│   ┌──────────────┐ ┌──────────────┐ ┌──────────────┐          │
│   │  ns=0 (tx)   │ │  ns=1 (cell) │ │  ns=da       │          │
│   │  交易数据     │ │  Cell元数据   │ │  (大数据)    │          │
│   └──────────────┘ └──────────────┘ └──────────────┘          │
│                                                                 │
│   每个叶子节点前缀包含其命名空间ID，使得：                         │
│   - 可以证明"某个命名空间的所有数据都在树中"                       │
│   - 轻客户端只需验证感兴趣的命名空间                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.3.3 Spora中的NMT应用

在Spora中，NMT用于承诺Segment中的Cell大数据：

```rust
// Segment结构中的NMT应用
pub struct SegmentWriter {
    chunks: Vec<ChunkMeta>,  // 每个Cell数据作为一个chunk
}

impl SegmentWriter {
    pub fn seal(&mut self) -> Result<SegmentRoot> {
        // 1. 构建NMT，所有chunk使用ns=DA_NAMESPACE
        let mut nmt = NMT::new(NS_CELL_DATA);
        
        for chunk in &self.chunks {
            nmt.append(chunk.hash());
        }
        
        // 2. 计算NMT根，作为segment_root
        let nmt_root = nmt.root();
        
        Ok(SegmentRoot { nmt_root, ... })
    }
}
```

#### 3.3.4 NMT vs 传统Merkle树

| 特性 | 传统Merkle树 | NMT |
|------|-------------|-----|
| **叶子标识** | 仅哈希值 | 哈希值 + 命名空间前缀 |
| **范围证明** | 困难 | 天然支持（按命名空间） |
| **轻客户端友好** | 一般 | 优秀（可忽略不相关命名空间） |
| **实现复杂度** | 简单 | 中等（需管理命名空间） |

#### 3.3.5 为什么Spora选择NMT？

1. **数据可用性抽样（DAS）**：轻客户端可以随机抽样验证大数据可用性，无需下载完整Segment
2. **命名空间隔离**：未来可扩展支持多种数据类型（交易、Cell、合约代码等）
3. **与Celestia生态兼容**：借鉴成熟的DA层设计方案

### 4.1 已实现

| 组件 | 状态 | 说明 |
|------|------|------|
| `cell_root` | ✅ 已集成 | 共识层完整实现，用于状态承诺 |

### 4.2 架构断层

当前实现的**问题**是数据分离未彻底执行：

```
设计目标：
┌─────────────────────────────────────────┐
│  RocksDB（索引层）                        │
│  - cell_output（元数据）                   │
│  - segment_info（指针: segment_id/offset/len）│
└─────────────────────────────────────────┘
                    ↓ 指针
┌─────────────────────────────────────────┐
│  Segment文件（DA层）                      │
│  - cell_data（实际大数据）                 │
│  - NMT承诺                               │
└─────────────────────────────────────────┘

当前实现：
┌─────────────────────────────────────────┐
│  RocksDB（索引层）                        │
│  - cell_output（元数据）                   │
│  - cell_data: Vec<u8>  ← ❌ 大数据直接存DB  │
│  - segment_info（未使用）                  │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  Segment文件（DA层）                      │
│  - 存在但孤立，未被共识层使用               │
└─────────────────────────────────────────┘
```

| 问题 | 严重程度 | 位置 |

## 5. 分阶段实现规划

### 5.1 阶段1：当前（共识闭环）

**目标**：确保共识层状态机完整

**已实现**：
- `cell_root` + `cell_commitment` 已集成
- GhostDAG + Cell状态转移已闭环

**标注**：
```rust
// 在文档和代码中明确标注
/// segment_root: 预留字段，待轻客户端阶段实现
pub segment_root: Hash, // TODO: DA层第二阶段启用
```

### 5.2 阶段2：数据分离（性能优化）

**目标**：执行"大数据不进DB"原则

**任务**：
1. 修改`CellMeta`存储逻辑：
   - 大Cell data → Segment文件
   - CellDB只存`SegmentInfo`指针
2. 共识层调用`SegmentWriter`：
   - 在Cell创建时写入Segment
   - 在Cell花费时保留引用

**注意**：此阶段仍不需要`segment_root`进区块头

### 5.3 阶段3：轻客户端支持（DA完整）

**目标**：支持不存储完整数据的轻客户端

**任务**：
1. 区块头添加`segment_root`
2. 实现完整NMT承诺计算
3. 实现P2P DA抽样协议
4. 轻客户端DA验证支持

## 7. 结论

| 问题 | 答案 |
|------|------|
| 三者是否重合？ | ❌ **不重合**，职责分离清晰 |
| `cell_commitment`是否多余？ | ❌ **不多余**，版本化抽象必要 |
| `segment_root`是否必要？ | ✅ **长期必要**，短期可选 |
| 当前实现问题？ | ⚠️ **数据分离未执行**，Cell大数据应走DA层 |
| 是否需要精简？ | ✅ 当前可只用`cell_root`，未来需要`segment_root` |

**最终建议**：

1. **保留三者设计**：职责清晰，不重合
2. **修复数据分离**：Cell大数据应存Segment，RocksDB只存指针
3. **当前阶段**：区块头只需`cell_root` + `cell_commitment`
4. **轻客户端阶段**：添加`segment_root`，启用完整DA层
